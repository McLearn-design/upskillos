Everything so far runs when **you** remember to run it, on **your** machine. Continuous integration (CI) runs it on every change, on machines you choose, and refuses to call a change done until it all passes.

```text
git push  ─►  GitHub  ─►  Ubuntu:   configure, build, test   ✓
                     ├─►  Windows:  configure, build, test   ✓
                     ├─►  macOS:    configure, build, test   ✗
                     ├─►  sanitizers: test under ASan, UBSan ✓
                     └─►  style:     check-format, clang-tidy ✓
```

It catches what one machine can't: code that only compiles with your compiler, a file you forgot to commit, a test that passes only on Linux. This lesson writes a **GitHub Actions** workflow. You can write and commit it without a GitHub account; the last step shows how to watch it run.

## Step 1 — A workflow: build and test on three systems

**This step: create `.github/workflows/ci.yml` with one job that configures, builds and tests on Ubuntu, Windows and macOS.**

GitHub runs every `.yml` file in `.github/workflows/`. The format is YAML: indentation shows structure (spaces only, never tabs), `key: value` sets things, and `- ` starts an item in a list.

| Line | Means |
|---|---|
| `on: push: branches: [main]` | run on every push to `main` ... |
| `pull_request:` | ... and on every pull request |
| `jobs: build-and-test:` | a **job**: steps that run on one fresh machine |
| `matrix: os: [...]` | run the job once per value: three machines, in parallel |
| `fail-fast: false` | if Windows fails, still finish macOS: you want every result |
| `runs-on: ${{ matrix.os }}` | which machine; `${{ }}` inserts a value |
| `uses: actions/checkout@v4` | a ready-made step: clone the repository |
| `run: ...` | a command, run in the repository folder |

The three commands are the ones you've typed all track, with one difference: `--config Release` and `--build-config Release`. On Windows, CMake's default generator is Visual Studio, a **multi-config** generator: one build folder holds Debug **and** Release, so `CMAKE_BUILD_TYPE` is ignored, and the build and CTest must each be told which one. On Linux and macOS (Makefiles, one configuration per folder) the extra options are harmless. Without them, the Windows job's `ctest` finds no tests to run.

Notice too that CI's Windows machine uses **MSVC**, not MinGW: the `if(MSVC)` warning flags in `CMakeLists.txt` finally get used.

```yaml file=.github/workflows/ci.yml
# Continuous integration: GitHub runs this on every push and pull
# request, and marks the commit with a green tick or a red cross.
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-and-test:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - name: Configure
        run: cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
      - name: Build
        run: cmake --build build --config Release
      - name: Test
        run: ctest --test-dir build --build-config Release --output-on-failure
```

```check
file .github/workflows/ci.yml -- The file goes in .github/workflows/, at the top of the repository.
matches .github/workflows/ci.yml "os:\s*\[\s*ubuntu-latest\s*,\s*windows-latest\s*,\s*macos-latest\s*\]" label="the matrix has ubuntu-latest, windows-latest and macos-latest"
contains .github/workflows/ci.yml "runs-on: ${{ matrix.os }}"
contains .github/workflows/ci.yml "actions/checkout@v4"
matches .github/workflows/ci.yml "cmake --build build --config Release" label="the build names its configuration"
matches .github/workflows/ci.yml "ctest --test-dir build (-C|--build-config) Release" label="ctest names its configuration" -- Visual Studio builds are multi-config: ctest needs --build-config Release.
```

## Step 2 — Sanitizers and style in CI

**This step: add two more jobs to `ci.yml`: `sanitizers` and `style`, both on Ubuntu.**

Each job starts on a fresh machine, so each checks out the code and configures again. Jobs run in parallel.

- **sanitizers**: the whole test suite with `-DSANITIZE=ON`. Lesson 5's bug passed every normal test; this job would have failed the colleague's pull request. Ubuntu's GCC has the sanitizers, so it doesn't matter whose machine lacks them.
- **style**: `check-format` and clang-tidy. A pull request that isn't formatted fails here, before a person spends time on it. The runner's shell is `bash`, so `src/*.cpp` expands as you'd expect.

Pin the tools in a real project. `ubuntu-latest` moves to a newer Ubuntu every couple of years, with a newer clang-format that may format some lines differently, and then `check-format` fails on code nobody touched. Teams pin the runner (`ubuntu-24.04`) or the tool version (`pip install clang-format==18.1.8`), and upgrade on purpose.

```yaml file=.github/workflows/ci.yml
# Continuous integration: GitHub runs this on every push and pull
# request, and marks the commit with a green tick or a red cross.
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-and-test:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - name: Configure
        run: cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
      - name: Build
        run: cmake --build build --config Release
      - name: Test
        run: ctest --test-dir build --build-config Release --output-on-failure

  sanitizers:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Configure with sanitizers
        run: cmake -S . -B build -DSANITIZE=ON
      - name: Build
        run: cmake --build build
      - name: Test
        run: ctest --test-dir build --output-on-failure

  style:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Configure
        run: cmake -S . -B build
      - name: Check formatting
        run: cmake --build build --target check-format
      - name: clang-tidy
        run: clang-tidy --quiet -p build src/*.cpp app/*.cpp
```

```check
contains .github/workflows/ci.yml "sanitizers:"
contains .github/workflows/ci.yml "-DSANITIZE=ON"
contains .github/workflows/ci.yml "--target check-format"
contains .github/workflows/ci.yml "clang-tidy"
```

## Step 3 — A README, and a commit

**This step: write `README.md`: what the project is, and how to build and test it. Then commit everything.**

A README is the project's front door: the first thing anyone sees on GitHub, and the first file a new colleague opens. Keep it to what a newcomer needs:

- one line saying what it is, and an example;
- how to build and test: the exact commands;
- anything unusual: here, the sanitizer build and the format target.

Lesson 7 installs this file with the program.

```text
git add -A
git commit -m "Add CI on three systems, and a README"
```

Once the project is on GitHub, you can show CI's status at the top of the README with a **badge**, an image GitHub draws from the latest run:

```text
![CI](https://github.com/YOU/interp/actions/workflows/ci.yml/badge.svg)
```

```markdown file=README.md
# interp

A small calculator language with variables, written in C++20.

    $ calc "rate = 3" "rate * (2 + 4)"
    = 3
    = 18

Build and test
--------------

    cmake -S . -B build
    cmake --build build
    ctest --test-dir build

`cmake -S . -B build-asan -DSANITIZE=ON` builds with AddressSanitizer
and UndefinedBehaviorSanitizer. `cmake --build build --target format`
formats the code.
```

```check
contains README.md "ctest --test-dir build"
git-tracked .github/workflows/ci.yml
git-tracked README.md
git-clean
```

## Step 4 — See it run

**This step: optional, and it needs a GitHub account. No checks.**

```text
gh repo create interp --private --source . --push
```

or, without the `gh` tool: create an empty repository on github.com (no README, no .gitignore), then

```text
git remote add origin https://github.com/YOU/interp.git
git push -u origin main
```

- A **remote** is another copy of the repository, here on GitHub. `origin` is the conventional name for the main one.
- `push -u` sends your commits and remembers `origin/main` as this branch's **upstream**, so later a plain `git push` is enough.

Open the repository's **Actions** tab: five jobs (three systems, sanitizers, style) start within seconds. Click one to see each step's output, exactly as in your terminal.

**Make it fail on purpose:** on a branch, break one row of `tests/interpreter_test.cpp`, push the branch, and open a pull request. The checks go red, and the pull request page says so. That's the point: in **Settings → Branches**, a *branch protection rule* can require the checks to pass before anything merges into `main`. From then on, `main` is green by rule, not by hope.
