# Lesson 34: Capstone — Registration and Login UI (HTMX-Powered)

**What you will build**
You will build the registration and login entry points of the application. The registration flow will validate input, hash the password, store the user, and auto-login. The login flow will verify credentials and establish a session. Both routes use HTMX to swap validation errors in-place without a full page reload, and use a flash message system to display one-time success or error messages.

**What you need to know first**
You need to know how to set up basic Flask routes and use Jinja templates from previous lessons. You should also be familiar with SQLite for basic data storage, as introduced earlier in this series.

**Terms used in this lesson**
- **Flash Message** — A temporary message stored in the session that is displayed to the user exactly once on the next request, then automatically cleared. It exists to provide immediate feedback (like "Login successful" or "Invalid credentials") after a redirect.
- **CSRF Token** — A unique, unpredictable value generated by the server and included in forms or headers. It exists to prevent Cross-Site Request Forgery attacks, ensuring that a state-changing request genuinely originated from the application's own UI.
- **HTMX Swapping** — The process where HTMX replaces a specific part of the DOM with HTML returned from an AJAX request. It exists to create single-page application interactivity without writing custom JavaScript, improving user experience by avoiding full page reloads.

**Objects and methods used**
- **`PasswordHasher`**
  - *What it is:* A utility from the `argon2` library for hashing passwords and verifying hashes.
  - *Implementation:* `ph = PasswordHasher()`
  - *Its use:* We use it to securely hash user passwords during registration and verify them during login.
  - *Type:* Class
  - *Responsibility:* Generates secure Argon2 hashes from plaintext passwords and verifies plaintext against existing hashes.
  - *Depends on:* The `argon2-cffi` library.
  - *Connects to:* Called by the registration and login route functions.
  - *Shape:* Internal implementation detail for security.
- **`flash`**
  - *What it is:* A Flask function to store a one-time message.
  - *Implementation:* `flash(message, category)`
  - *Its use:* We use it to queue success and error messages for the user.
  - *Type:* Function
  - *Responsibility:* Appends a message to the session's flash queue.
  - *Depends on:* A configured Flask `SECRET_KEY` to sign the session.
  - *Connects to:* Called by route handlers; consumed by `get_flashed_messages()`.
  - *Shape:* Framework API boundary.
- **`get_flashed_messages`**
  - *What it is:* A Flask template global function to retrieve flash messages.
  - *Implementation:* `get_flashed_messages(with_categories=True)`
  - *Its use:* We use it in the base template to render any pending messages.
  - *Type:* Function
  - *Responsibility:* Reads and clears messages from the session's flash queue.
  - *Depends on:* The session context.
  - *Connects to:* Called within Jinja templates.
  - *Shape:* Framework API boundary.

## Concept Unit: Base template with HTMX and flash messages

### The Problem
We need a consistent layout across all pages of our application that includes a navigation bar, a way to display temporary feedback messages to the user (like "Logged out"), and the HTMX library wired up to automatically include CSRF protection on all requests. How do we provide this shared structure without duplicating HTML in every single route?

### Introduce the concept in isolation
We can use a base template that defines the shell of the page. Let's look at how flash messages work in isolation using a temporary Flask script.

```python
from flask import Flask, flash, get_flashed_messages, render_template_string
import secrets

app = Flask(__name__)
app.config['SECRET_KEY'] = secrets.token_hex(32)

@app.route('/')
def test_flash():
    flash('This is a test message', 'info')
    return render_template_string('''
        {% with messages = get_flashed_messages(with_categories=True) %}
            {% for category, message in messages %}
                [{{ category }}] {{ message }}
            {% endfor %}
        {% endwith %}
    ''')

if __name__ == '__main__':
    with app.test_client() as c:
        print(c.get('/').data.decode())
```

**Output:**
```
[info] This is a test message
```
This proves that calling `flash()` stores the message, and `get_flashed_messages()` within the template immediately retrieves and clears it. This pattern is called a **flash message**.

## Concept Unit: Registration route

### The Problem
When a user signs up, they might provide invalid data (like a username that's too short). If we use standard form submission, the server returns the page with errors, causing a full page reload. This resets the user's scroll position and causes a flash of unstyled content. How do we validate the form and show errors seamlessly?

### Introduce the concept in isolation
We can use HTMX to submit the form via AJAX and replace only the form itself with the server's response. Let's see how HTMX handles a non-200 HTTP response.

```python
from flask import Flask, request
app = Flask(__name__)

@app.route('/submit', methods=['POST'])
def submit():
    return '<form id="f">Error!</form>', 422

with app.test_client() as c:
    response = c.post('/submit')
    print(f"Status: {response.status_code}")
    print(f"Content: {response.data.decode()}")
```
**Output:**
```
Status: 422
Content: <form id="f">Error!</form>
```
By returning a 422 Unprocessable Entity status, HTMX knows the request completed but the input was invalid. If the form uses `hx-swap="outerHTML"`, HTMX will replace the old form with this new HTML containing the error message. This is called **HTMX Swapping**.

## Concept Unit: Login route with HTMX redirect

### The Problem
When a user logs in via an HTMX form, we don't want to just swap a fragment; we want to redirect them entirely to the application's main page (e.g., `/notes`). However, if a standard 302 redirect is returned to an AJAX request, the browser follows it transparently, and HTMX will swap the *entire* dashboard HTML into the login form's container, breaking the layout. How do we tell HTMX to perform a full-page client-side redirect instead?

### Introduce the concept in isolation
We can use a special HTTP header to instruct HTMX to change the browser's location. Let's see how we set headers in Flask.

```python
from flask import Flask, make_response
app = Flask(__name__)

@app.route('/test-redirect')
def test_redirect():
    resp = make_response('', 204)
    resp.headers['HX-Redirect'] = '/notes'
    return resp

with app.test_client() as c:
    response = c.get('/test-redirect')
    print(f"Status: {response.status_code}")
    print(f"HX-Redirect: {response.headers.get('HX-Redirect')}")
```
**Output:**
```
Status: 204
HX-Redirect: /notes
```
By returning a `204 No Content` and setting the `HX-Redirect` header, HTMX will intercept this response and execute `window.location = '/notes'`. This is a **client-side redirect**.

```python
from flask import make_response

LOGIN_HTML = '''
<form id="login-form" hx-post="/login" hx-target="#login-form" hx-swap="outerHTML">
    {% if error %}<div class="flash flash-error">{{ error }}</div>{% endif %}
    <input type="text" name="username" placeholder="Username" autocomplete="username">

    <label><input type="checkbox" name="remember"> Remember me</label>
    <button type="submit">Login</button>
</form>
'''

INVALID = 'Invalid username or password.'
DUMMY_HASH = PasswordHasher().hash('dummy-equalize-timing')

@app.route('/login', methods=['GET', 'POST'])
def login():
    if request.method == 'GET':
        return render_template_string('<html><body>' + LOGIN_HTML + '</body></html>', error=None)
    
    username = request.form.get('username','').strip()
    password = request.form.get('password','')
    user = None  # (lookup from DB in real app)
    
    if user is None:
        try: ph.verify(DUMMY_HASH, password)
        except VerifyMismatchError: pass
        return render_template_string(LOGIN_HTML, error=INVALID), 401
        
    session.clear()
    session['user_id'] = user['id']
    
    resp = make_response('', 204)
    resp.headers['HX-Redirect'] = '/notes'
    return resp
```

## Concept Unit: CSRF protection wired into HTMX

### The Problem
If a user is logged into our app, their browser will automatically send their session cookie with any request to our domain. A malicious site could create a hidden form that submits a POST request to our `/register` or `/notes` endpoints. Since the browser includes the cookie, our server thinks the request is legitimate. How do we verify that a request actually originated from our UI?

### Introduce the concept in isolation
We can require a secret token that only our application knows. The malicious site cannot read this token because of the Same-Origin Policy.

```python
import hmac, secrets
from flask import Flask, request, session, abort

app = Flask(__name__)
app.config['SECRET_KEY'] = 'test'

@app.route('/api/do', methods=['POST'])
def do_action():
    token = request.headers.get('X-CSRF-Token', '')
    expected = session.get('_csrf', '')
    if not expected or not hmac.compare_digest(token, expected):
        abort(403)
    return 'Success'

with app.test_request_context('/api/do', method='POST', headers={'X-CSRF-Token': 'wrong'}):
    session['_csrf'] = 'right'
    try:
        do_action()
    except Exception as e:
        print(f"Error: {e.code}")
```
**Output:**
```
Error: 403
```
This proves that if the token in the header doesn't match the one in the session, the request is rejected with a 403 Forbidden. This is a **CSRF Token** check.

```python
def get_csrf_token():
    if '_csrf' not in session:
        session['_csrf'] = secrets.token_hex(32)
    return session['_csrf']

def check_csrf():
    token = request.headers.get('X-CSRF-Token', '')
    expected = session.get('_csrf', '')
    return bool(expected) and hmac.compare_digest(token, expected)

@app.before_request
def csrf_protect():
    if request.method in ('POST', 'PUT', 'DELETE', 'PATCH'):
        if request.path.startswith('/api/') or request.headers.get('HX-Request') == 'true':
            if not check_csrf():
                from flask import abort
                abort(403)

app.jinja_env.globals['csrf_token'] = get_csrf_token
```

- `if request.method in ('POST', ...)` restricts the check to state-changing methods (GET requests should never change state, so they don't need CSRF protection).
- `request.headers.get('HX-Request') == 'true'` checks if the request was made by HTMX.
- `abort(403)` immediately terminates the request with a Forbidden status.
- `app.jinja_env.globals['csrf_token'] = get_csrf_token` makes the function callable from any Jinja template (like we used in `base.html`).

### CS lens
`hmac.compare_digest` is critical here. Standard string comparison (`==`) compares character by character and returns `False` the moment it finds a mismatch. An attacker can repeatedly send tokens and measure the microsecond differences in response time to slowly guess the token character by character. `compare_digest` always takes the exact same amount of time regardless of where the mismatch occurs, defeating timing attacks.

### SE lens
Security should be "secure by default." By placing the CSRF check in a `@app.before_request` hook, we protect all current and future endpoints automatically. Developers don't have to remember to add `@csrf_protect` decorators to every single route. If they forget, the app is still secure.

## Closing

### Connect the pieces
We have built a robust, secure entry point for the application. The flow looks like this:
1. A user visits `/register`. The `base.html` template generates a CSRF token.
2. The user submits the form. HTMX intercepts the submission, attaches the CSRF token header, and sends an AJAX POST request.
3. The `@app.before_request` hook verifies the token.
4. The route validates the input. If invalid, it returns 422 with errors. HTMX swaps the form in-place, preserving the user's focus.
5. If valid, the password is mathematically hashed with Argon2, stored, and the session is established.
6. A success message is flashed, and the server returns a 204 with an `HX-Redirect` header.
7. HTMX follows the header, navigating the browser to the dashboard.
8. The new page loads, and `get_flashed_messages()` displays the success message exactly once.
9. When the user clicks Logout, the session is wiped, another flash message is queued, and the user is redirected back to the login screen.
