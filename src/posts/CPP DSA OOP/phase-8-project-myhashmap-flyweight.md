## Part 1: Assembling `MyHashMap`

Every piece from Lessons 8.1–8.4 comes together here, in one class — the exact pattern Phase 2's `MyVector` project and Phase 5's `MyLinkedList`/`MyVector` project both followed: build the pieces separately, across several lessons, then assemble them into one real, complete, usable type.

```cpp
#include <iostream>
#include <vector>
#include <memory>
#include <string>

class MyHashMap {
private:
    struct HashNode {
        std::string key;
        int value;
        std::unique_ptr<HashNode> next;
        HashNode(const std::string& k, int v) : key(k), value(v), next(nullptr) {}
    };

    std::vector<std::unique_ptr<HashNode>> table;
    int tableSize;
    int entryCount;
    static constexpr double MAX_LOAD_FACTOR = 0.75;

    int hashWithSize(const std::string& key, int size) const {
        long long h = 0;
        for (char c : key) {
            h = (h * 31 + c) % size;
        }
        return static_cast<int>(h);
    }

    int hash(const std::string& key) const {
        return hashWithSize(key, tableSize);
    }

    double loadFactor() const {
        return static_cast<double>(entryCount) / tableSize;
    }

    void rehash() {
        int newSize = tableSize * 2;
        std::vector<std::unique_ptr<HashNode>> newTable(newSize);

        for (auto& chainHead : table) {
            HashNode* current = chainHead.get();
            while (current != nullptr) {
                int newIndex = hashWithSize(current->key, newSize);
                auto newNode = std::make_unique<HashNode>(current->key, current->value);
                newNode->next = std::move(newTable[newIndex]);
                newTable[newIndex] = std::move(newNode);
                current = current->next.get();
            }
        }

        table = std::move(newTable);
        tableSize = newSize;
    }

public:
    MyHashMap(int initialSize = 8) : tableSize(initialSize), entryCount(0) {
        table.resize(tableSize);
    }

    void insert(const std::string& key, int value) {
        if (loadFactor() >= MAX_LOAD_FACTOR) {
            rehash();
        }

        int index = hash(key);
        HashNode* current = table[index].get();
        while (current != nullptr) {
            if (current->key == key) {
                current->value = value;
                return;
            }
            current = current->next.get();
        }

        auto newNode = std::make_unique<HashNode>(key, value);
        newNode->next = std::move(table[index]);
        table[index] = std::move(newNode);
        entryCount++;
    }

    bool find(const std::string& key, int& outValue) const {
        int index = hash(key);
        HashNode* current = table[index].get();
        while (current != nullptr) {
            if (current->key == key) {
                outValue = current->value;
                return true;
            }
            current = current->next.get();
        }
        return false;
    }

    bool remove(const std::string& key) {
        int index = hash(key);
        std::unique_ptr<HashNode>* current = &table[index];
        while (*current != nullptr) {
            if ((*current)->key == key) {
                *current = std::move((*current)->next);
                entryCount--;
                return true;
            }
            current = &(*current)->next;
        }
        return false;
    }

    int size() const { return entryCount; }
};
```

## Part 2: Reload the JSON checkpoint data into `MyHashMap`

Recall Phase 5's project checkpoint: `people.json`, generated by Python, parsed with `nlohmann::json`, loaded into a `PersonList` (a linked list). Reload the same data source, but this time build a hash map from name to age, and compare lookup speed against a linear scan through the equivalent linked list.

```cpp
#include <fstream>
#include <nlohmann/json.hpp>
#include <chrono>

int main() {
    std::ifstream file("people.json");
    nlohmann::json j;
    file >> j;

    MyHashMap ageByName;
    std::vector<std::pair<std::string, int>> asVector;   // for the linear-scan comparison

    for (const auto& entry : j) {
        std::string name = entry["name"];
        int age = entry["age"];
        ageByName.insert(name, age);
        asVector.push_back({name, age});
    }

    std::string target = asVector[asVector.size() / 2].first;   // pick a real name to search for

    // --- Hash map lookup ---
    auto start1 = std::chrono::high_resolution_clock::now();
    int foundAge;
    bool found1 = ageByName.find(target, foundAge);
    auto end1 = std::chrono::high_resolution_clock::now();

    // --- Linear scan lookup ---
    auto start2 = std::chrono::high_resolution_clock::now();
    bool found2 = false;
    int scanAge = -1;
    for (const auto& p : asVector) {
        if (p.first == target) {
            scanAge = p.second;
            found2 = true;
            break;
        }
    }
    auto end2 = std::chrono::high_resolution_clock::now();

    std::cout << "hash map: found=" << found1 << " age=" << foundAge
              << " time=" << std::chrono::duration_cast<std::chrono::nanoseconds>(end1 - start1).count()
              << "ns" << std::endl;
    std::cout << "linear scan: found=" << found2 << " age=" << scanAge
              << " time=" << std::chrono::duration_cast<std::chrono::nanoseconds>(end2 - start2).count()
              << "ns" << std::endl;

    return 0;
}
```

For a tiny 10-entry dataset (Phase 5's original `people.json` size), the two will likely be close, possibly even favoring the linear scan slightly — hashing has real fixed overhead (Lesson 8.1's cost), and for tiny n, O(1)-with-overhead can lose to O(n)-with-almost-none. This is worth confirming directly, not glossing over, because it's a genuinely honest, important result: **Big-O describes scaling, not a guarantee that the asymptotically better algorithm always wins for small inputs** — exactly Phase 3's framing, recurring here concretely.

## Part 3: The Flyweight pattern — deduping repeated string data

### The problem: the same string, stored a thousand times over

Imagine loading a large dataset where a field repeats constantly — a "category" or "department" field across a million records, drawn from only a few dozen distinct actual values ("Engineering", "Sales", "Marketing", repeated over and over). Storing a full, separate `std::string` copy of `"Engineering"` in every one of 400,000 records wastes an enormous amount of memory on pure duplication — the same bytes, copied hundreds of thousands of times.

### The fix: store each unique string exactly once, shared

```cpp
class StringPool {
private:
    MyHashMap indexByString;        // maps a string's content to a small integer ID
    std::vector<std::string> strings;   // the actual, UNIQUE string storage — one copy per distinct value

public:
    int intern(const std::string& s) {
        int existingId;
        if (indexByString.find(s, existingId)) {
            return existingId;   // already seen this exact string — reuse its ID, no new storage
        }

        int newId = strings.size();
        strings.push_back(s);
        indexByString.insert(s, newId);
        return newId;
    }

    const std::string& get(int id) const {
        return strings[id];
    }
};
```

`intern()` is the Flyweight pattern's core operation, named directly after a real technique used in real language runtimes (Python interns short strings and identifiers internally for exactly this reason — this isn't a toy exercise, it's a genuine, widely-used real-world technique). The first time a given string is seen, it's stored once, and a small integer ID is handed back. Every subsequent occurrence of the *same* string content, no matter how many times it recurs, reuses that same ID — `MyHashMap` does the O(1)-average work of recognizing "have I seen this exact string before?"

```cpp
int main() {
    StringPool pool;

    std::vector<int> categoryIds;
    std::vector<std::string> rawCategories = {
        "Engineering", "Sales", "Engineering", "Marketing", "Sales", "Engineering"
        // imagine this repeating across 400,000 real records
    };

    for (const auto& cat : rawCategories) {
        categoryIds.push_back(pool.intern(cat));
    }

    // categoryIds now holds small ints, e.g. [0, 1, 0, 2, 1, 0]
    // the ACTUAL string storage holds only 3 entries total, not 6 (or 400,000)

    for (int id : categoryIds) {
        std::cout << pool.get(id) << " ";
    }
    std::cout << std::endl;

    return 0;
}
```

`categoryIds` holds six small integers; `pool`'s actual string storage holds exactly three strings — `"Engineering"`, `"Sales"`, `"Marketing"` — no matter how many total records reference them. This is the entire payoff: **the memory cost scales with the number of *distinct* values, not the number of *occurrences*** — for a real dataset with a handful of distinct categories repeated across hundreds of thousands of records, this is a dramatic, genuinely practical memory savings, made possible entirely by the O(1)-average `find` this phase spent five lessons building.

## What this cost / bought us

| | Storing every string directly, everywhere it appears | Flyweight, via `MyHashMap` (this project) |
|---|---|---|
| Memory for repeated values | O(total occurrences) | O(distinct values) |
| Lookup cost to find/create a shared value | N/A | O(1) average — this phase's entire payoff |
| Extra indirection | None | One integer ID per occurrence, one lookup to resolve it back to the string |
| Where this is used in real systems | — | Python's string interning, compiler symbol tables, many real-world data-deduplication systems |
