# Game Studio build plan

**Status:** Phase 1 foundation is implemented. The remaining phases below are the source of truth for future work.

Game Studio is a new, isolated lab for building complete browser games while learning the ideas behind them. It must grow without changing or destabilizing Sprite Forge, Tile Mapper, Sim Lab, or any existing game. Existing tools remain independent; Game Studio reads their exports through versioned adapters.

## Product promise

A beginner should be able to open an example, understand what each part does, change it visually, press Play, and see the result. As they progress, the same project should reveal real game-development concepts and code instead of trapping them in a simplified toy format.

The editor should eventually support a broad range of 2D Phaser games. A single editor cannot supply every specialized system out of the box, so “any game” means a stable project model, extensible components, scripts, assets, scenes, and plugins that do not impose a genre.

## Non-negotiable boundaries

1. Do not edit the internals or saved-document formats of existing labs to integrate them.
2. Import Sprite Forge and Tile Mapper data through adapters owned by `src/labs/game-studio/`.
3. Keep the editable project document separate from the Phaser runtime. The editor may migrate old documents; the runtime only receives a validated current document.
4. Every saved project has a `kind` and integer `version`. Add a migration before changing stored structure.
5. Examples create copies. Loading or editing an example must never mutate a shared template.
6. Beginner controls and explanations stay visible by default. Advanced code and engine details are disclosed gradually.
7. Use the app’s global theme tokens and shared `oc-*` styles. Do not create a separate theme system.
8. Generated catalog files are regenerated by the repository scripts; they are never edited by hand.

## Current foundation — complete

- New auto-discovered `/lab/game-studio` lab; existing labs are untouched.
- Version 1 project schema with projects, scenes, entities, transforms, appearance, physics, behavior, settings, and asset slots.
- Defensive JSON import and JSON export.
- IndexedDB local saving with a last-project preference.
- Scene tree, add/select/duplicate/delete actions, drag positioning, and an Inspector.
- Distinct Edit and Play modes.
- Phaser Play preview with top-down movement, Arcade Physics, gravity, bouncing, and object collisions.
- Learning drawer with blank, movement, and physics examples plus step-by-step explanations.
- Searchable, three-pane example library with live Phaser output, complete copyable code, explanations above each code excerpt, and safe “Load a copy” behavior.
- Six working projects, led by the complete Neon Maze Chase game with a maze, 43 energy dots, collision walls, patrol enemies, score, lives, respawning, and win/lose states.
- Searchable code-pattern library with 12 runnable patterns for input, motion, platform jumping, patrols, animation, game feel, simple AI, cooldowns, and game math.
- Per-object learner scripts with a documented frame API, live preview, validation, and insertion from the pattern library. Loop syntax, browser globals, network APIs, and dynamic code construction are blocked in this beginner runtime.
- Links to open Sprite Forge and Tile Mapper independently.
- Unit coverage for the project model’s creation, import validation, and immutable entity operations.

## Phase 2 — dependable editor core

**Goal:** make the current foundation safe for longer projects.

- Add a project browser: create, rename, duplicate, archive, and intentionally delete local projects.
- Add multiple scenes and startup-scene selection.
- Add layer ordering, visibility, locking, folders, and multi-selection.
- Add resize/rotate handles, grid and object snapping, guides, zoom, pan, and fit-to-view.
- Group a drag gesture into one undo entry; persist undo only for the current session.
- Add keyboard shortcuts with an in-app shortcut reference.
- Validate all numeric Inspector input and show errors next to the field.
- Add recovery snapshots and a visible “last saved” timestamp.
- Add component and browser tests for selection, editing, saving, import, and mode switching.

**Exit test:** a learner can build and reopen a three-scene project without losing work, and every destructive action is recoverable or clearly confirmed.

## Phase 3 — asset pipeline

**Goal:** use original art and maps without coupling the tools.

- Define `GameAssetV1` records for image, sprite sheet, animation, tile map, audio, font, and data assets.
- Implement a Sprite Forge adapter that reads its existing versioned document/export and copies a PNG plus animation metadata into the game project.
- Implement a Tile Mapper adapter that reads its existing export and copies tileset, layers, dimensions, and collision data into the game project.
- Add ordinary file upload for PNG, JPEG, WebP, SVG, audio, JSON, and supported tile-map files.
- Add an asset browser with thumbnails, names, tags, usage count, replace, and safe delete.
- Store large blobs outside the JSON project record in IndexedDB and reference them by stable asset ID.
- Revoke object URLs and cap previews so long sessions do not leak memory.
- Add attribution/license fields for imported assets.

**Exit test:** a sprite can be drawn in Sprite Forge, imported, animated, placed in two scenes, exported, reopened, and played without modifying Sprite Forge.

## Phase 4 — components and gameplay

**Goal:** cover the systems used across common 2D game genres.

- Sprite renderer, text, shapes, camera, audio source, particle emitter, tile map, and UI components.
- Arcade body shapes, sensors/triggers, collision layers, gravity controls, and collision callbacks.
- Input maps that name actions such as `move-left` or `jump` instead of hard-coding keys.
- Built-in behaviors for platform movement, top-down movement, follow, patrol, projectile, health, timer, collectible, and scene transition.
- Prefabs with local overrides.
- Global variables, per-scene variables, tags, and event channels.
- Camera follow, bounds, zoom, shake, fade, and multiple cameras.
- Audio mixer groups and accessible volume controls.

**Exit test:** the included guided projects can produce a platformer, top-down adventure, puzzle, shooter, and menu-driven game using the same component model.

## Phase 5 — code without a dead end

**Goal:** let learners progress from visual settings to real programming.

- Add a Monaco code workspace for project scripts and reusable modules.
- Expand the existing safe per-object script surface into project scripts and reusable modules; preserve the small object API as the beginner entry point.
- Generate readable starter code from components, then allow the learner to take ownership of it.
- Supply typed Game Studio APIs and autocomplete for scene, entity, input, physics, time, camera, assets, and events.
- Run learner code in a sandboxed worker or iframe with a narrow message API, timeouts, and useful mapped errors.
- Add a console, debugger pause/step support where practical, object inspection, and performance counters.
- Preserve scripts as source files in project export rather than hiding behavior in serialized closures.
- Add escape hatches to Phaser APIs with an explicit compatibility boundary.

**Exit test:** a learner can begin with a built-in behavior, inspect its equivalent code, modify it, create a custom component, and diagnose a runtime error without leaving the editor.

## Phase 6 — learning from zero to mastery

**Goal:** make learning part of the editor rather than a separate manual.

- Turn each example into a versioned lesson with goal, concepts, annotated project diff, experiments, checks, hints, and extension challenges.
- Create paths for fundamentals, programming, 2D math, physics, animation, level design, UI, audio, save systems, procedural generation, AI, optimization, and publishing.
- Show explanations beside the relevant scene object, Inspector field, code range, or running output.
- Add “change this and predict what happens” experiments.
- Track lesson progress locally and keep project work independent of progress records.
- Include capstones that combine earlier systems and provide rubrics instead of one expected solution.
- Add accessibility lessons and checks for keyboard input, contrast, text size, motion, captions, and remapping.

**Exit test:** a first-time user can follow a path from placing one object through publishing an original multi-scene game, while an experienced user can skip lessons and use the same editor directly.

## Phase 7 — packaging and publishing

**Goal:** make projects portable and playable away from the editor.

- Export one ZIP containing a manifest, project JSON, scripts, assets, licenses, and a pinned runtime version.
- Import ZIP defensively: validate paths, sizes, types, schema, and references before writing anything.
- Export a static web build with a generated entry page, Phaser runtime, project bundle, loading screen, and responsive canvas.
- Add playable-build settings for aspect ratio, scaling, orientation, controls, accessibility, and metadata.
- Add deterministic export tests and a project compatibility fixture for every schema version.
- Consider sharing/publishing only after local export is reliable; it must be an optional layer over the portable format.

**Exit test:** an exported game runs from a static host, and its editable source can be reimported into a fresh browser profile.

## Phase 8 — advanced systems

- Visual shader and effects stack with code escape hatch.
- Navigation/pathfinding and behavior trees.
- Dialogue, quest, inventory, and data-table tools supplied as optional packages.
- Procedural generation helpers, deterministic random seeds, replays, and test bots.
- Custom component/plugin SDK with documented lifecycle and project migrations.
- Performance profiler, draw-call view, asset budget, object pooling, and mobile checks.
- Collaboration/version-control friendly text export after schema stabilization.

## Project format direction

The current version uses one JSON record and reserves `assets` for future adapters. Keep these top-level concepts stable:

```text
project
├── identity: kind, version, id, name, timestamps
├── settings: viewport, scale, physics, startup scene
├── scenes[]
│   └── entities[]
│       ├── identity and hierarchy
│       └── components: transform, display, physics, behavior, scripts…
├── assets[]: metadata and references to separately stored blobs
├── input actions
└── scripts/modules
```

Do not place browser object URLs, Phaser instances, DOM nodes, functions, or class instances in the saved document. IDs are stable references. Runtime objects are disposable projections built from the document.

## Example and lesson contract

Each future example should include:

- a stable ID and content version;
- learner level and prerequisites;
- a short result-focused description;
- the concepts it teaches;
- a fresh project factory or portable fixture;
- ordered experiments and explanations;
- expected observable outcomes rather than hidden implementation checks;
- at least one extension challenge;
- a compatibility test that opens and runs it.

Examples should teach one main idea first, then combine ideas in larger projects. The library needs filters for level, genre, system, and estimated time before it grows beyond a small list.

## Validation required for each phase

Run focused tests for changed pure modules, the catalog navigation test when lab metadata changes, and the production build. Manually verify light and dark themes, the app’s floating-window size, keyboard-only access, project recovery, and the full Edit → Play → Edit loop. Keep at least one saved compatibility fixture for every released project version.

## Next implementation slice

Start with Phase 2 in this order: project browser, multiple scenes, transform handles/snapping, grouped undo gestures, then recovery snapshots. After that, define `GameAssetV1` and implement Sprite Forge import before adding more gameplay components. This order protects learner projects before the document becomes more complex.
